# 一、缓存三件套：穿透、击穿、雪崩

## 面试问：你项目里怎么防止缓存穿透、击穿、雪崩？

这三个问题我项目里封装了一个统一的 CacheClient 来处理，不是散落在各个 Service 里各自为战。

### 缓存穿透

穿透是指查询一个数据库里根本不存在的数据，缓存永远不会命中，每次都打到 DB，恶意攻击时会把 DB 打垮。

项目里的方案是空值缓存：查 DB 返回 null 时，往 Redis 写一个特殊的哨兵值 `__NULL__`，TTL 设短一点（2分钟左右）。下次同样的请求进来，读到哨兵值直接返回 null，不再查 DB。

为什么用固定字符串 `__NULL__` 而不是空字符串：空字符串和"缓存不存在"无法区分，用固定哨兵值可以明确判断"这是一个已知的空结果"。

### 缓存击穿

击穿是指热点 key 过期的瞬间，大量并发请求同时打到 DB，DB 扛不住。

项目里用互斥锁方案：拿不到缓存时，先用 Redisson 的 tryLock 抢锁，只有一个线程能拿到锁去查 DB 并重建缓存，其他线程 sleep 50ms 后重试读缓存。拿到锁后还有一个 Double Check——再查一次缓存，因为等待期间可能已经有线程重建好了，避免重复回源。

### 缓存雪崩

雪崩是指大量 key 同时过期，瞬间大量请求打到 DB。

项目里的方案是随机 TTL：写缓存时不用固定过期时间，而是基础时间加上一个随机值（ThreadLocalRandom 生成），让不同 key 的过期时间错开，避免集中失效。

### 三种防护的统一封装

CacheClient 提供了 queryWithPassThrough（防穿透）和 queryWithMutex（防穿透+防击穿）两个方法，所有缓存读取都走这两个方法，不需要每个 Service 自己写重复逻辑。用户信息、餐厅信息等都走 queryWithMutex，同时享受穿透和击穿防护。

# 二、并发安全：先查后写的陷阱

## 面试问：你项目里有哪些并发安全问题，怎么解决的？

"先查后写"是最常见的并发陷阱：查询和写入之间有时间窗口，并发请求可能同时通过查询，都执行写入，导致重复数据。

### 用户注册并发安全

问题：注册时先查用户名是否存在，再插入。并发下两个请求同时通过查询，都插入同一用户名。

两层防护：

第一层是 Redisson 分布式锁，锁 key 按用户名维度（lock:user:register:{username}），不同用户名互不影响。tryLock(0, 10, TimeUnit.SECONDS)，拿不到锁直接抛异常，不排队等待。加锁范围覆盖整个"查用户名 → 插入"区间，串行化并发请求。

第二层是数据库唯一索引兜底（uk_username、uk_phone），捕获 DuplicateKeyException 转成友好的业务异常。锁防的是正常并发，索引防的是极端情况下锁失效或跨实例的漏网之鱼。

### 评价提交并发安全

问题：同一用户对同一订单并发提交两次，绕过"已评价"校验。

锁 key 按用户+订单维度（lock:review:submit:{userId}{orderId}），精确到一次评价行为。拿不到锁直接抛"请勿重复提交评价"，不需要等待。

### 热门榜单刷新并发保护

问题：定时任务和手动刷新同时触发，多线程并发删旧榜单、查 DB、写 ZSet，数据混乱。

锁 key 全局唯一（lock:hot:rank:refresh），tryLock 拿不到直接 return，不抛异常。因为榜单刷新是幂等操作，第一个线程刷完数据就是最新的，其他线程没必要等待或报错。

### 释放锁的安全写法

所有场景释放锁时都加了 isHeldByCurrentThread() 判断：先判断 locked 为 true，再判断锁还在当前线程手里，两个条件都满足才 unlock。原因是指定了 leaseTime=10 秒，如果业务超时锁自动过期，此时其他线程已经拿到了这把锁，不加判断会误释放别人的锁。

# 三、N+1 查询问题

## 面试问：什么是 N+1 查询，你项目里怎么处理的？

N+1 查询是指查出 N 条主记录后，在循环里对每条记录再单独查一次关联数据，产生 N+1 次 SQL，数据量大时性能极差。

项目里 getUserReviewHistory 方法之前就有这个问题：查出用户的 N 条评价后，循环里每条评价都单独 selectById 查餐厅名，10条评价 = 11次 SQL。

修复方案：先 selectList 拿到所有评价，用 stream 收集所有 restaurantId 到一个 Set，一次 selectBatchIds 批量查出所有餐厅，转成 Map<Long, Restaurant> 方便 O(1) 取值，再 stream 映射 VO 时直接从 Map 里取餐厅名。N+1 次 SQL 变成固定 2 次 SQL，无论数据量多大都是 2 次。

OrderServiceImpl 的 listOrders 方法也是同样的模式，批量查餐厅信息后转 Map 再映射 VO。

# 四、MQ 消息可靠性保障

## 面试问：你怎么保证 RabbitMQ 消息不丢失？

消息丢失有三个环节：生产者发送时丢、Broker 存储时丢、消费者处理时丢。项目里三个环节都有对应的保障。

### 生产者确认（防发送丢失）

开启 publisher-confirm-type: correlated，消息到达交换机后触发 ConfirmCallback 回调。ack 为 true 说明到达交换机，ack 为 false 说明发送失败，在回调里触发重试逻辑。

同时开启 publisher-returns: true，消息到了交换机但路由不到队列时触发 ReturnsCallback，在回调里标记路由失败并触发重试。

发送消息时把消息元数据存入 Redis（key 是 mq:msgId:{msgId}），ConfirmCallback 确认成功后延迟1秒删除（延迟是为了等 ReturnsCallback 可能的路由失败标记），失败时从 Redis 取出元数据重试。

### 消息持久化（防 Broker 丢失）

队列和消息都设置为持久化（QueueBuilder.durable），Broker 重启后消息不丢失。

### 消费者去重（防重复消费）

消费者处理消息前，先用 MqDedupService 的 tryMarkConsumed 方法做幂等检查：用 setIfAbsent 往 Redis 写 mq:consumed:{msgId}，写成功说明首次消费，写失败说明重复消费直接跳过。TTL 设 72 小时，覆盖消息重试的时间窗口。

业务异常时调用 rollback 方法删除去重标记，允许消息重试再次处理。

### 死信队列兜底

评价审核队列配置了死信交换机，消息重试 3 次失败后路由到 review.audit.dlx.queue，由专门的消费者处理或人工介入，不会无声无息地丢失。

# 五、ES 数据同步解耦

## 面试问：MySQL 和 ES 的数据怎么保持同步，为什么要用 MQ 异步？

评分更新的链路是：用户提交评价 → AI 审核通过 → 评分更新写库 → 删除 Redis 缓存 → 发 MQ 消息 → RestaurantEsSyncConsumer 消费 → 从 MySQL 查最新数据 → 同步到 ES。

为什么不直接在评分更新后同步调用 ES：评分更新本身是在 MQ 消费者里触发的，如果再同步调用 ES，ES 一旦抖动就会拖慢消费速度，导致消息积压。改成异步 MQ 后，ES 同步失败只影响搜索数据的实时性，不影响评分写库和缓存更新的主流程。

ES 同步的容错设计：消费者里先查 MySQL，如果餐厅已被删除就从 ES 删文档，如果存在就 save（ES 的 save 是 upsert 语义，存在则更新，不存在则新增），不需要区分新增和修改场景。

数据一致性的接受程度：搜索结果的评分延迟几秒更新是可以接受的，用户感知不到。如果是强一致场景（比如库存扣减），就不能用 ES 存，必须走 MySQL。

# 六、缓存预热与批量写入优化

## 面试问：热门榜单是怎么做缓存预热的，有什么性能优化？

榜单刷新完成后，立即预热 TopN 餐厅的详情缓存，避免用户查榜单时缓存全部未命中、大量请求打到 DB。

预热流程：从 ZSet 取出 TopN 的餐厅 ID，一次 selectBatchIds 批量查 MySQL，转成 Map 后批量写入 Redis。

批量写入的优化点：原来的写法是先 multiSet 写入所有 key，再循环 N 次单独 expire 设置过期时间，N 次网络 IO。优化后改用 Redis Pipeline，把所有 set+expire 合并成一次网络往返，用 executePipelined 执行，每个 key 用 connection.stringCommands().set() 同时指定值和过期时间，N 次 IO 变成 1 次。

查询热门餐厅时也用了 multiGet 批量读缓存，一次网络 IO 取出所有 key 的值，而不是循环单独 get。

# 七、SQL 原子更新防并发

## 面试问：评分更新怎么防止并发写入导致数据错误？

评分更新不是先查出当前评分再加减，而是直接用 SQL 原子计算：updateRatingBySQL 方法在 SQL 里用聚合函数重新计算该餐厅所有已审核评价的平均分，一条 UPDATE 语句完成，不存在"读-改-写"的并发窗口。

这是处理统计类更新的标准做法：让数据库用一条 SQL 完成计算和写入，而不是在应用层读出来算完再写回去。应用层的"读-改-写"在并发下会产生覆盖写问题（两个线程同时读到旧值，各自加1后写回，实际只加了1次）。

# 八、敏感词过滤双层方案

## 面试问：评价内容的安全审核是怎么做的？

项目里用了两层过滤，各有分工：

第一层是 DFA 算法本地快速过滤，在评价提交时同步执行，耗时不到 10ms。维护一个敏感词库（存在 Redis Set 里），用 DFA 算法匹配评价内容，命中明显敏感词直接拒绝，不进入后续流程。DFA 的优势是时间复杂度 O(n)，只和文本长度有关，不受敏感词库大小影响。

第二层是 AI 语义审核，通过 RabbitMQ 异步触发，不阻塞用户提交。AI 能识别 DFA 无法覆盖的语义问题，比如文字与评分不一致（5星但内容全是差评）、隐晦表达的违规内容等，返回 APPROVE/REJECT/MANUAL_REVIEW 三种状态。

两层配合：DFA 快速拦截明显违规，AI 处理语义层面的复杂情况，既保证了响应速度，又提升了审核质量。

# 九、订单超时自动取消

## 面试问：订单超时自动取消是怎么实现的？

用 Redis ZSet 实现延时队列：订单创建后，把订单 ID 和超时时间戳（用餐时间+30分钟）作为 score 存入 ZSet（order:no_show:delay:zset）。

定时任务 OrderNoShowCancelTask 每 5 秒扫描一次，用 rangeByScore 取出 score 小于当前时间戳的订单，这些就是已超时的订单，执行取消逻辑。

并发安全：扫描任务用手写 SETNX 锁（而不是 Redisson），锁 key 按订单 ID 维度（order:no_show:lock:{orderId}），防止多实例重复处理同一订单。这里用手写 SETNX 而不是 Redisson，是因为场景简单，只需要基本互斥，不需要可重入和看门狗，手写更轻量。

为什么用 Redis ZSet 而不是 RabbitMQ 延时队列：RabbitMQ 的 TTL+死信队列方案在消息量大时，死信队列头部未过期消息会阻塞后面已过期消息的投递（队列是 FIFO 的）。Redis ZSet 按 score 排序，rangeByScore 直接取到期消息，没有这个问题。

# 十、可观测性：Prometheus 监控

## 面试问：你项目里怎么做监控的？

项目集成了 Micrometer + Prometheus，暴露 /actuator/prometheus 端点，Prometheus 定期拉取指标数据，Grafana 可视化展示。

CacheClient 里埋了自定义指标：每次缓存请求都用 Counter 记录 cache.request.total、cache.hits.total、cache.misses.total，打上 biz（业务名）、strategy（穿透/击穿防护策略）、result（命中/未命中/空值命中）三个 tag，可以按业务维度分析缓存命中率。同时用 Timer 记录 cache.latency，监控缓存读取的延迟分布。

这样做的好处：出现性能问题时，可以直接在 Grafana 上看到是哪个业务的缓存命中率下降，或者哪个策略的延迟升高，快速定位问题，而不是靠猜。

# 十一、高频追问

## Q：缓存和数据库的一致性怎么保证？

项目里用的是"先更新数据库，再删缓存"的策略，而不是"先删缓存，再更新数据库"。

原因：先删缓存再更新数据库，在删缓存和更新数据库之间，其他线程可能读到旧数据并重新写入缓存，导致缓存里一直是旧值。先更新数据库再删缓存，即使删缓存失败，下次读缓存未命中时会从数据库读到最新值。

还有一个短暂不一致窗口：更新数据库成功但还没删缓存的瞬间，读到的是旧缓存。这个窗口极短（毫秒级），业务上可以接受。

## Q：Redis Pipeline 和普通批量操作有什么区别？

普通的 multiSet 是一次网络 IO，但 multiSet 不支持同时设置过期时间，所以还需要循环 N 次 expire，每次 expire 都是一次网络 IO，总共 N+1 次。

Pipeline 是把多个命令打包成一批发给 Redis，Redis 顺序执行后一次性返回所有结果，只有 1 次网络往返。项目里用 executePipelined 把 set+expire 合并，N 次 IO 变成 1 次，在预热大量缓存时效果明显。

## Q：为什么用 DFA 算法做敏感词过滤，而不是直接用 contains 或正则？

contains 需要对每个敏感词都遍历一次文本，时间复杂度 O(n*m)，n 是文本长度，m 是敏感词数量，敏感词库大时极慢。正则同理，且正则引擎有回溯问题，复杂模式下可能出现灾难性回溯（ReDoS）。

DFA（确定有限自动机）把所有敏感词构建成一棵前缀树，匹配时只需遍历一次文本，时间复杂度 O(n)，和敏感词库大小无关，适合高频调用的场景。

## Q：消息去重为什么用 setIfAbsent 而不是先 get 再 set？

先 get 再 set 是两步操作，不是原子的。并发下两个线程可能同时 get 到 null，都认为是首次消费，都执行业务逻辑，去重失效。setIfAbsent 是原子操作，只有一个线程能写成功，天然保证幂等。

## Q：你项目里有哪些地方用了事务，事务和缓存怎么配合？

评价提交（createReview）和用户注册（register）都加了 @Transactional。

事务和缓存的配合有一个坑：如果在事务里删缓存，事务还没提交时缓存已经删了，其他线程读缓存未命中，回源 DB 读到的是事务提交前的旧数据，又写回缓存，等事务提交后缓存里还是旧值。

正确做法是在事务提交后再删缓存，可以用 Spring 的 @TransactionalEventListener(phase = AFTER_COMMIT) 监听事务提交事件，在事务提交后触发缓存删除。项目里评分更新后删缓存就是通过事件机制异步触发的。

## Q：分布式锁和数据库唯一索引，两个都要吗，不是重复了吗？

不重复，两者防的是不同层面的问题。

分布式锁防的是"并发请求同时通过业务校验"，减少无效的 DB 写入，保护 DB 不被大量重复请求打到。但锁有失效的可能（超时、异常、多实例时钟漂移等），不能作为唯一保障。

数据库唯一索引是最终的强一致性保障，即使锁失效，DB 层面也不会写入重复数据。两者配合，锁是第一道防线，索引是最后的兜底。

# 十二、面试总结（一段话版本）

> 我项目里的性能优化和风险防范主要体现在几个维度：缓存层面封装了 CacheClient，统一处理穿透（空值哨兵）、击穿（Redisson 互斥锁+Double Check）、雪崩（随机 TTL）三种问题，并用 Prometheus 埋点监控缓存命中率和延迟；并发安全层面，用户注册和评价提交都用了 Redisson 分布式锁+数据库唯一索引双层防护，热门榜单刷新用全局锁保证幂等；查询优化层面，修复了 getUserReviewHistory 的 N+1 问题，改成批量查询+Map 映射，热门榜单预热用 Pipeline 把 N 次 set+expire 合并成 1 次网络 IO；消息可靠性层面，生产者确认+消费者去重+死信队列三层保障，ES 同步改成异步 MQ 解耦主流程；评价审核用 DFA 本地快速过滤+AI 语义审核双层方案，兼顾速度和质量。
