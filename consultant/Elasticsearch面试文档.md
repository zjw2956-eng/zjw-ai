# 一、ES 基础概念

## 面试问：ES 是什么，和 MySQL 有什么区别？

Elasticsearch 是基于 Lucene 的分布式全文搜索引擎，核心能力是对文本做倒排索引，支持毫秒级全文检索。

和 MySQL 的核心区别：

| 维度 | MySQL | Elasticsearch |
|------|-------|---------------|
| 数据模型 | 表/行/列（关系型） | 索引/文档（JSON） |
| 查询方式 | SQL，精确匹配为主 | DSL，全文检索为主 |
| LIKE 查询 | 前缀通配符全表扫描，慢 | 倒排索引，毫秒级 |
| 事务支持 | 完整 ACID | 不支持事务 |
| 数据一致性 | 强一致 | 近实时（写入后约1秒可查） |
| 适用场景 | 业务数据存储、精确查询 | 全文搜索、日志分析 |

项目里的分工：MySQL 是主数据源，存储餐厅完整业务数据；ES 是搜索层，只存搜索需要的字段，用户搜索餐厅时走 ES，不走 MySQL。

## 面试问：ES 的核心概念有哪些？

类比 MySQL 来理解：Index（索引）对应 Table，Document（文档）对应一行数据，Field（字段）对应列，Mapping 对应表结构定义，Shard（分片）是数据的水平切分单元。

项目里有一个 `restaurant` 索引，每条餐厅记录是一个 Document，包含名称、菜系、地址、评分等字段。

# 二、项目 ES 能力全景

## 面试问：你项目里 ES 用来做什么？

项目里 ES 承担以下职责：

- **餐厅全文搜索**：用户输入关键词，在餐厅名称、地址、简介、菜系上做全文检索，支持分类筛选、价格区间、评分过滤，接口是 `GET /api/restaurant/search`
- **搜索结果高亮**：搜索命中的关键词用 `<em>` 标签包裹，前端渲染时高亮显示
- **索引管理**：提供管理员接口手动重建索引（`POST /api/admin/es/restaurant/rebuild`）
- **数据同步**：评分更新后通过 MQ 异步把最新数据同步到 ES
- **启动初始化**：应用启动时自动检查并初始化索引，首次启动全量导入 MySQL 数据

# 三、索引设计与 Mapping

## 面试问：你的 ES 索引是怎么设计的？

项目用 `RestaurantEsDoc` 类加 Spring Data ES 注解来定义 Mapping，字段设计思路如下：

- `name`（餐厅名称）、`address`（地址）、`description`（简介）：都是 Text 类型，写入和搜索时走 IK 分词，支持全文检索
- `category`（菜系）：用了 MultiField，主字段是 Keyword 类型（不分词，用于精确筛选），子字段是 Text 类型（分词，用于关键词模糊搜索）
- `avgPrice`（人均消费）、`rating`（评分）：Double 类型，用于范围过滤和排序
- `status`、`isDeleted`：Integer 类型，用于 filter 过滤，不参与相关度评分

## 面试问：为什么 category 要用 MultiField？

`category` 有两种使用场景，对字段类型的要求是矛盾的：

- 用户从下拉框选"川菜"做精确筛选，需要 Keyword 类型（不分词，精确 term 查询）
- 用户在搜索框输入"川"做模糊搜索，需要 Text 类型（分词，match 查询）

如果只用 Keyword，搜索"川"匹配不到"川菜"；如果只用 Text，精确筛选"川菜"可能因为分词问题出现误匹配。MultiField 让同一个字段同时具备两种能力，精确筛选走主字段 Keyword，模糊搜索走子字段 `category.text`，这是 ES 处理这类场景的标准做法。

# 四、分词器选型

## 面试问：你用了什么分词器，为什么这样选？

项目用 IK 分词器，这是中文 ES 场景的标准选择。IK 有两种模式：

- `ik_max_word`：最细粒度切分，尽可能多切词。比如"北京烤鸭餐厅"会切成"北京"、"烤鸭"、"餐厅"、"北京烤鸭"等多个词条
- `ik_smart`：最粗粒度切分，语义优先。同样的句子只切成"北京烤鸭"、"餐厅"

项目里写入时用 `ik_max_word`，搜索时用 `ik_smart`，这是一个经典组合：

写入时尽量多建索引词条，保证各种搜索词都能命中（召回率高）；搜索时用语义更完整的切分，避免把"鸭"单独作为搜索词带来噪音（精准度高）。两者配合，既能搜到，又不会搜出太多无关结果。

# 五、全文搜索实现

## 面试问：你的搜索接口是怎么实现的？

项目用 `ElasticsearchOperations` 构建 BoolQuery 复合查询，整体结构分三层：

**must 层（影响相关度评分）**：对用户输入的关键词做多字段全文搜索，同时在餐厅名称、简介、菜系子字段上匹配，开启了 fuzziness 容错，允许用户输入有少量拼写错误时仍能搜到结果。

**filter 层（纯过滤，不影响评分）**：固定过滤营业中且未删除的餐厅，再根据用户传入的参数可选过滤菜系（精确匹配）、价格区间（范围查询）、最低评分（范围查询）。

**排序**：先按相关度分数降序，再按评分降序，保证最相关且评分高的餐厅排在前面。

## 面试问：must 和 filter 有什么区别？

must 里的条件会参与相关度评分（_score）计算，影响结果排序；filter 里的条件只做是/否过滤，不影响评分，而且 ES 会对 filter 结果做缓存，性能比 must 更好。

所以项目里关键词搜索放 must（需要影响排序），状态、分类、价格这些精确条件放 filter（纯过滤，不需要影响排序，还能享受缓存加速）。

## 面试问：什么是 fuzzy 查询，你为什么用它？

fuzzy 查询允许搜索词和文档词条之间有一定的编辑距离（字符增删改），用来处理用户输入拼写错误的场景。

项目里用的是 `fuzziness("AUTO")`，ES 会根据词长自动决定允许的错误数：词长 1-2 不允许错误，3-5 允许1个字符错误，超过5个允许2个字符错误。同时开启了 `fuzzyTranspositions`，允许相邻字符换位。另外设置了 `maxExpansions(50)` 限制模糊展开的词条数量，防止性能抖动。

# 六、高亮显示

## 面试问：搜索结果高亮是怎么实现的？

ES 高亮的原理：ES 在返回搜索结果时，对匹配到关键词的字段，用指定的前后缀标签把关键词包裹起来，前端渲染时就能高亮显示。

项目里配置了对 `name` 和 `description` 两个字段做高亮，前缀是 `<em>`，后缀是 `</em>`。ES 返回的 SearchHit 里会带一个 highlightFields 集合，里面存的是已经加了标签的字段值。

处理逻辑是：拿到搜索结果后，检查每个 hit 的 highlightFields，如果 name 或 description 有高亮版本，就用高亮版本替换原始字段值再返回给前端。这样前端直接渲染就能看到关键词高亮效果，不需要前端自己处理。

# 七、数据同步方案

## 面试问：MySQL 和 ES 的数据怎么保持同步？

这是 ES 使用中最核心的工程问题。常见方案有三种：

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 同步双写 | 写 MySQL 同时写 ES | 实时性高 | 耦合高，ES 故障影响主流程 |
| 异步 MQ | 写 MySQL 后发消息，消费者写 ES | 解耦，主流程不受 ES 影响 | 有短暂延迟 |
| Binlog 监听（Canal） | 监听 MySQL binlog 变更同步到 ES | 完全解耦，对业务无侵入 | 引入新组件，运维复杂 |

项目选择异步 MQ 方案，触发链路是：用户提交评价 → AI 审核通过 → 评分更新写库 → 删除 Redis 缓存 → 发 MQ 消息 → `RestaurantEsSyncConsumer` 消费 → 从 MySQL 查最新数据 → 同步到 ES。

为什么不用同步双写：评分更新本身是在 MQ 消费者里触发的，如果再同步调用 ES，ES 一旦抖动就会拖慢消费速度，导致消息积压。改成异步 MQ 后，ES 同步失败只影响搜索数据的实时性，不影响评分写库和缓存更新的主流程。

同步逻辑本身也做了容错：先查 MySQL，如果餐厅已被删除就从 ES 删文档，如果存在就 upsert（ES 的 save 是 upsert 语义，存在则更新，不存在则新增），不需要区分新增和修改场景。

## 面试问：数据同步会不会有一致性问题？

会有短暂的不一致窗口，MySQL 已更新但 ES 还没同步，这是异步方案的固有代价。

项目里的接受程度：搜索结果的评分延迟几秒更新是可以接受的，用户感知不到。如果是强一致场景（比如库存扣减），就不能用 ES 存，必须走 MySQL。

# 八、索引初始化与重建

## 面试问：ES 索引是怎么初始化的？

项目用 `RestaurantIndexInitializer` 实现 `CommandLineRunner` 接口，在 Spring Boot 启动完成后自动执行。

流程是：先检查 Redis 里有没有 `es:restaurant:index:initialized` 这个标记，有则跳过；没有则先创建索引和 Mapping，再从 MySQL 全量导入餐厅数据，最后写入初始化标记（300天过期）。

为什么用 `CommandLineRunner` 而不是 `@PostConstruct`：`@PostConstruct` 在 Bean 初始化阶段执行，此时 Spring 容器可能还没完全就绪。`CommandLineRunner` 在整个容器启动完成后执行，更安全。

为什么用 Redis 标记而不是每次检查 ES 索引是否存在：检查索引存在只能防止重复建索引，但不能防止重复全量导入数据。用 Redis 标记可以同时跳过建索引和全量导入两个步骤，避免每次重启都重新导入数据。

## 面试问：索引重建是怎么做的？

重建流程分三步：删旧索引（含所有文档）→ 建新索引并 putMapping → 从 MySQL 全量导入。

什么时候需要重建：Mapping 发生变更时（ES 大多数字段类型不支持原地修改，必须重建）、数据大量不一致需要全量重新同步时、分词器配置变更时。

生产环境重建索引的风险是重建期间索引不可用，搜索会失败。标准做法是蓝绿索引方案：建新索引导入数据，切换别名指向新索引，再删旧索引，整个过程搜索不中断。项目是小规模场景，直接重建即可。

# 九、Spring Data ES 使用方式

## 面试问：你用 Spring Data ES 的哪些 API？

项目里用了两种方式，各有分工：

**ElasticsearchRepository（简单 CRUD）**：继承这个接口后自动获得 save（upsert）、saveAll（批量 upsert）、deleteById、findById 等基础操作。项目里的索引管理和数据同步都用这个，不需要写 DSL。

**ElasticsearchOperations（复杂查询和索引管理）**：用于构建复杂的 BoolQuery（多条件过滤、高亮、排序），以及索引的创建、删除、putMapping 等操作。搜索接口和索引初始化都用这个。

两者的关系：`ElasticsearchRepository` 底层也是用 `ElasticsearchOperations` 实现的，只是封装了常用 CRUD，屏蔽了 DSL 细节。简单场景用 Repository，复杂查询必须用 Operations 手写 DSL。

# 十、高频追问

## Q：ES 的倒排索引是什么原理？

正排索引是"文档 ID → 文档内容"，适合按 ID 查文档。倒排索引反过来，是"词条 → 包含该词条的文档 ID 列表"，适合按关键词查文档。

举例：文档1是"北京烤鸭餐厅"，文档2是"北京川菜馆"。倒排索引里，"北京"对应 [文档1, 文档2]，"烤鸭"对应 [文档1]，"川菜"对应 [文档2]。搜索"北京"时直接查倒排索引，O(1) 找到结果，不需要全表扫描，这就是 ES 搜索快的根本原因。

## Q：ES 写入后为什么不能立即查到？

ES 写入流程是：数据先写入内存 Buffer，每隔1秒 refresh 一次把 Buffer 里的数据写到 Segment（此时才可查），每隔30分钟 flush 一次把 Segment 持久化到磁盘。

这个1秒的 refresh 间隔导致 ES 是近实时（Near Real-Time）而不是实时。项目里的数据同步本来就是异步的，这1秒影响不大。如果需要立即可查可以手动调 refresh，但频繁 refresh 影响写入性能，生产环境不建议用。

## Q：ES 分页有什么坑？

ES 默认分页用 from + size，但有个限制：from + size 不能超过 `index.max_result_window`，默认是10000。超过这个值会报错。

项目里餐厅数量有限，用户也不会翻到很深的页，这个限制不会触发。

深度分页的解决方案：`search_after` 基于上一页最后一条记录的排序值翻页，性能好但不支持跳页；`scroll` 适合全量导出，不适合实时搜索。

## Q：ES 和 MySQL 数据不一致怎么处理？

项目里的处理思路：首先接受短暂不一致，搜索结果的评分延迟几秒是可以接受的。其次可以做定时全量对账，定时任务对比 MySQL 和 ES 的数据，发现不一致则重新同步（项目里是后续优化点）。最后重建索引兜底，数据严重不一致时直接调 `rebuildIndex()` 全量重建。

## Q：为什么不直接用 MySQL 的 LIKE 查询，非要引入 ES？

LIKE 查询有四个核心问题：

1. 性能差：前缀通配符导致全表扫描，无法走索引，数据量大时极慢
2. 不支持分词：搜"川"搜不到"川菜馆"，除非用 `LIKE '%川%'`，但这样噪音更多
3. 不支持相关度排序：MySQL 不能按匹配程度排序，只能按固定字段排序
4. 不支持高亮：MySQL 不能返回带高亮标签的结果

ES 解决了以上所有问题，这是引入 ES 的核心价值。

## Q：ES 集群的分片和副本是什么？

分片（Shard）是把索引数据水平切分到多个节点，提升存储容量和查询并发。副本（Replica）是每个分片的备份，提升可用性，主分片故障时副本顶上。

项目是单节点开发环境，默认1个主分片、0个副本。生产环境通常设置3个主分片、1个副本。

# 十一、面试总结（一段话版本）

> 我项目里 ES 主要用于餐厅全文搜索。索引设计上，文本字段用 IK 分词器（写入 ik_max_word、搜索 ik_smart），菜系字段用 MultiField 同时支持精确筛选和模糊搜索。搜索实现用 BoolQuery，关键词搜索放 must 影响相关度排序，状态、分类、价格过滤放 filter 不影响评分且有缓存，同时开了 fuzziness 容错和高亮返回。数据同步方面，评分更新后通过 MQ 异步触发 ES 同步，解耦主流程，避免 ES 抖动影响消息消费速度。索引初始化用 CommandLineRunner 加 Redis 标记实现幂等，避免每次重启重复导入。
