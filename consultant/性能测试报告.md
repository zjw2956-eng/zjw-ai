## 二、场景一：缓存层压测

### 2.1 测试目的

对比有缓存（餐厅详情）与无缓存（餐厅列表）两个接口在相同并发量下的性能差异，验证 Redis 缓存对系统吞吐量的提升效果。

### 2.2 接口说明

**有缓存组**：`GET /api/restaurant/{id}`

该接口在 `RestaurantServiceImpl.getRestaurantById` 中使用 `CacheClient.queryWithMutex` 实现缓存，缓存 key 为 `restaurant:info:{id}`，TTL 72 小时，缓存未命中时加互斥锁回源数据库，并同步生成 AI 摘要写入缓存。

**无缓存对比组**：`GET /api/restaurant/list`

该接口 `listRestaurants` 直接走 MyBatis-Plus 分页查询，**未做缓存**。原因是列表接口支持分类、价格区间、评分等多维度过滤参数，参数组合数量庞大，缓存 key 难以管理，且数据实时性要求较高，因此不适合缓存。

### 2.3 测试配置

| 配置项 | 有缓存组 | 无缓存对比组 |
|---|---|---|
| 接口 | `GET /api/restaurant/1` | `GET /api/restaurant/list` |
| 线程数 | 100 | 100 |
| 循环次数 | 20 | 20 |
| 总请求数 | 2000 | 2000 |
| 认证方式 | JWT Token（Header: Authorization） | JWT Token（Header: Authorization） |

### 2.4 测试结果

| 指标 | 有缓存（餐厅详情） | 无缓存（餐厅列表） |
|---|---|---|
| 样本数 | 2000 | 2000 |
| 平均响应时间 | 47ms | 6ms |
| 最小响应时间 | 1ms | 4ms |
| 最大响应时间 | 2686ms | 41ms |
| 标准偏差 | 295.60 | 1.89 |
| 吞吐量 | 405.8/sec | 133.7/sec |
| 异常率 | 0% | 0% |

### 2.5 结果分析

**吞吐量**：有缓存组 405.8/sec，是无缓存组 133.7/sec 的约 **3 倍**，Redis 缓存对并发吞吐量的提升效果显著。

**响应时间**：有缓存组均值 47ms 反而高于无缓存组 6ms，原因在于餐厅详情接口的缓存回填逻辑（`buildRestaurantVO`）包含了 AI 摘要生成（调用通义千问 API），冷启动时耗时较长，拉高了整体均值。最大值 2686ms 和标准偏差 295.60 偏大，也印证了少量请求触发 AI 调用导致的响应抖动。

**无缓存组**均值 6ms、标准偏差 1.89，响应极为稳定，说明 MyBatis-Plus 分页查询本身性能良好，数据库在当前数据量下不是瓶颈。

### 2.6 测试过程中遇到的问题

**问题 1：JMeter CSV 首行被当作数据读取，导致 401 未登录**

- 现象：所有请求返回 `未登录或登录已过期`
- 原因：CSV Data Set Config 中"忽略首行"配置为 False，导致 `username,token` 表头被当作实际 token 发送
- 解决：将"忽略首行"设置为 True

**问题 2：POST 请求报 `Content-Type 'text/plain' is not supported`**

- 现象：JMeter 发送 POST 请求时服务端报 `HttpMediaTypeNotSupportedException`
- 原因：JMeter 默认 Content-Type 为 `text/plain`，而接口需要 `application/json`
- 解决：在 HTTP 信息头管理器中添加 `Content-Type: application/json`

**问题 3：Redis 缓存中存在脏数据导致 JSON 解析异常**

- 现象：查询餐厅详情时报 `cn.hutool.json.JSONException: A JSONObject text must begin with '{'`
- 原因：Redis 中 `restaurant:info:1` 存储了格式不正确的旧数据（非标准 JSON）
- 解决：执行 `redis-cli del restaurant:info:1` 清除脏数据后恢复正常

## 四、场景三：缓存击穿防护验证

### 4.1 测试目的

手动删除餐厅缓存后，模拟 50 个线程同时请求同一餐厅详情，验证以下两点：

1. `CacheClient.queryWithMutex` 互斥锁机制能否防止缓存击穿（只有一个线程回源数据库）
2. AI 摘要的逻辑过期方案能否防止多线程重复调用 AI

### 4.2 接口说明

`GET /api/restaurant/1`

缓存击穿场景：缓存失效瞬间大量并发请求同时到达，若无保护机制，所有请求都会穿透到数据库，造成数据库压力激增。

本系统使用 `CacheClient.queryWithMutex` 方案：缓存未命中时，通过 Redisson `RLock.tryLock` 抢锁，只有抢到锁的线程才能回源数据库并重建缓存，其余线程等待后重试读缓存。

### 4.3 测试配置

| 配置项 | 值 |
|---|---|
| 接口 | `GET /api/restaurant/1` |
| 线程数 | 50（同时启动） |
| 循环次数 | 1 |
| 总请求数 | 50 |
| 前置操作 | `redis-cli del restaurant:info:1`（清除缓存，模拟缓存失效） |

### 4.4 测试结果

| 指标 | 值 |
|---|---|
| 样本数 | 50 |
| 平均响应时间 | 2171ms |
| 最小响应时间 | 1716ms |
| 最大响应时间 | 2509ms |
| 标准偏差 | 111.31 |
| 吞吐量 | 19.9/sec |
| 异常率 | 0% |

### 4.5 结果分析

50 个并发请求全部成功，异常率 0%，互斥锁防击穿机制正常工作。

均值 2171ms 较高，原因是缓存冷启动时触发了 AI 摘要同步生成（调用通义千问 API），这是第一次请求必须承担的代价。标准偏差 111.31 相对较小，说明大多数线程都在等待锁释放后命中了缓存，响应时间集中，**没有出现大量线程同时打穿数据库的情况**，互斥锁机制生效。

### 4.6 测试过程中发现的问题与解决方案

#### 问题：AI 摘要被多线程重复调用

**现象**：

50 个并发请求中，日志出现多条"准备调用 AI 生成摘要"，AI 被重复调用多次，而预期是只调用一次。

**根因分析**：

`CacheClient.queryWithMutex` 在抢锁失败后存在一段兜底逻辑，直接调用了 `dbFallback.apply(id)`：

```java
// 问题代码（抢锁失败后的兜底回源）
R retryResult = dbFallback.apply(id);  // 直接触发 AI 调用
if (retryResult == null) {
    setNullValue(key, emptyTtlSeconds, ...);
    return null;
}
setWithRandomTtl(key, retryResult, ...);
```

这段代码的本意是"兜底防止用户拿不到数据"，但实际上每个抢锁失败的线程都会独立执行一次 AI 调用，完全绕过了互斥锁的保护意图，导致 AI 被并发调用多次。

**解决方案**：

分两步修复：

**第一步**：注释掉 `queryWithMutex` 中抢锁失败后的兜底回源逻辑。抢不到锁的线程等待 50ms 后重试读缓存，缓存还没建好则返回 null，由上层业务决定如何处理。

```java
// 修复后：抢锁失败只重试读缓存，不回源
locked = lock.tryLock(LOCK_GET_TIME, LOCK_TTL_SECONDS, TimeUnit.SECONDS);
if (!locked) {
    Thread.sleep(LOCK_RETRY_SLEEP_MILLIS);
    String retryJson = stringRedisTemplate.opsForValue().get(key);
    if (retryJson != null && !retryJson.isBlank()) {
        return JSONUtil.toBean(retryJson, type);
    }
    return null;  // 缓存还没建好，返回 null，不触发 AI
}
```

**第二步**：将 AI 摘要的缓存策略从互斥锁改为**逻辑过期方案**，彻底解决 AI 重复调用问题。

逻辑过期方案的核心思路：
- 缓存数据中额外存储一个逻辑过期时间字段（`CacheData<T>` 包装类）
- 缓存命中时，若逻辑时间未过期，直接返回数据
- 若逻辑时间已过期，**立即返回旧数据**（不阻塞用户），同时异步提交重建任务到线程池
- 异步重建时通过 Redisson 锁保证只有一个线程执行重建，其余线程继续返回旧数据
- 缓存物理 TTL 设为 7 天（远大于逻辑过期时间），保证数据不会真正消失

新增 `CacheData` 包装类：

```java
@Data
@AllArgsConstructor
@NoArgsConstructor
public class CacheData<T> {
    private T data;
    private LocalDateTime expireTime;
}
```

`RestaurantServiceImpl.getSummary` 改造后的逻辑：

```java
private String getSummary(Long restaurantId) {
    String key = Constants.REDIS_RESTAURANT_SUMMARY_KEY + restaurantId;
    // 先尝试逻辑过期读取（命中则立即返回，过期则异步重建）
    String cached = cacheClient.queryWithLogicalExpire(...);
    if (cached != null) {
        return cached;
    }
    // 缓存未命中（冷启动），同步生成并写入逻辑过期缓存
    String summary = buildSummaryFromDbAndAi(restaurantId);
    if (summary != null) {
        cacheClient.setWithLogicalExpire(key, summary, REDIS_RESTAURANT_SUMMARY_EXPIRE_TIME);
    }
    return summary;
}
```

**修复效果**：

修复后重新测试，日志中 AI 摘要调用仅出现一次（冷启动同步生成），后续 49 个并发请求均命中缓存或返回旧摘要，AI 调用次数从多次降为 **1 次**，问题解决。

## 五、场景四：热门榜单 QPS 压测

### 5.1 测试目的

### 7.5 测试过程中发现的问题与解决方案

#### 问题一：`getUserReviews` 工具调用报 SQL 语法错误

**现象**：

AI 调用 `getUserReviews` 工具时，日志报错：

```
SQLSyntaxErrorException: You have an error in your SQL syntax;
... near ') AND is_deleted=0' at line 1
SQL: SELECT ... FROM restaurant WHERE id IN ( ) AND is_deleted=0
```

**根因分析**：

`ReviewServiceImpl.getUserReviewHistory` 中，当用户没有任何评价记录时，`reviews` 列表为空，`restaurantIds` 是空 Set，直接传入 `selectBatchIds(restaurantIds)` 会生成 `WHERE id IN ()` 的非法 SQL，MySQL 不支持 IN 空括号语法。

```java
// 问题代码
Set<Long> restaurantIds = reviews.stream()
        .map(Review::getRestaurantId).collect(Collectors.toSet());
List<Restaurant> restaurantList = restaurantMapper.selectBatchIds(restaurantIds); // 空集合直接报错
```

**解决方案**：

在调用 `selectBatchIds` 前加空集合判断，提前返回空列表：

```java
Set<Long> restaurantIds = reviews.stream()
        .map(Review::getRestaurantId).collect(Collectors.toSet());
if (restaurantIds.isEmpty()) {
    return new ArrayList<>();
}
List<Restaurant> restaurantList = restaurantMapper.selectBatchIds(restaurantIds);
```

**修复文件**：[ReviewServiceImpl.java](src/main/java/cn/zjw/service/impl/ReviewServiceImpl.java)

#### 问题二：AI 部分回答使用英文

**现象**：部分请求 AI 用英文回复，未遵守中文要求。

**根因**：`system.txt` 系统提示词中未明确要求 AI 始终用中文回答，模型在某些情况下会默认切换为英文。

**解决方案**：在 `src/main/resources/system.txt` 中补充"请始终使用中文回答用户问题"的指令。

#### 问题三：Redis 记忆内容看起来像乱码

**现象**：Redis 中 `chat:memory:{memoryId}` 存储的内容显示混乱，疑似乱码。

**结论**：这是正常现象，不是 bug。LangChain4j 将完整的对话历史（包括工具调用请求 `ToolExecutionRequest` 和工具执行结果 `ToolExecutionResult`）序列化为 JSON 存储，内容结构复杂、体积较大，在 Redis 客户端直接查看时显示混乱，实际数据完整正确。

### 7.6 测试结论

AI 聊天接口在 5 并发下基本稳定，会话记忆隔离正常。测试过程中发现并修复了 `getUserReviews` 工具的空集合 SQL 异常，该 bug 会导致没有评价记录的用户触发工具调用时返回 500 错误。英文回答问题通过完善系统提示词可解决。
