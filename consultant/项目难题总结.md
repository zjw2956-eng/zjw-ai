# 二、难题一：RabbitMQ 能跑不难，难的是怎么把“可靠性”真正补齐

## 1. 问题背景

项目里我把几个耗时或解耦价值高的业务改成了异步：
- 评价创建后异步 AI 审核
- 订单确认超时后自动取消
- 评价通过/删除后异步刷新餐厅评分

一开始 RabbitMQ 接上并不难，生产者发消息、消费者收消息很快就能跑通。  
但我很快意识到，**“能跑通”不等于“业务可靠”**。

因为只要发生下面任意一种情况，业务就会出问题：
- 消息发出后没有真正到交换机
- 到了交换机但路由不到队列
- 消费过程中异常，消息反复重投
- 重复消息导致状态被多次修改
- 某条消息丢了，评价会一直停留在 `PENDING`

这时我意识到，面试官真正想听的不是“我会 RabbitMQ”，而是：

> 你怎么保证消息不丢、怎么避免重复消费、怎么做失败兜底？

---

## 2. 我当时的思考过程

我最开始的想法其实很简单：
- 生产者 `convertAndSend()`
- 消费者 `@RabbitListener`
- 失败抛异常让框架重试

但这很快暴露出两个问题：

### 第一，生产者视角看，发送不是“调用成功就一定成功”
`convertAndSend()` 返回不报错，不代表：
- 一定到了 exchange
- 一定路由到了 queue

所以我不能只看“代码执行没报错”。

### 第二，消费者视角看，RabbitMQ 天生是 at-least-once
只要是至少投递一次，就必须接受一个事实：

> **重复消费不是偶发 bug，而是分布式消息系统的常见现象。**

所以我的思路从“怎么把消息发出去”变成了：

1. 发送端怎么确认消息真的发到了正确位置
2. 失败后怎么拿到原始消息进行重试
3. 消费端怎么保证重复消息不会重复执行业务
4. 最终失败后怎么兜底，而不是直接丢消息

---

## 3. 最终方案

我最后做的是一套“生产者可靠发送 + 消费者幂等 + 死信兜底”的完整链路。

### 生产者侧
我在发送前先生成 `msgId`，把这条消息的：
- exchange
- routingKey
- message body
- retryCount

先缓存到 Redis，再发送 MQ，并且带上：
- `messageId`：给消费者做去重
- `CorrelationData(msgId)`：给生产者确认回调用

然后在 `RabbitMQConfig` 里配置：
- `ConfirmCallback`：确认消息是否到达交换机
- `ReturnsCallback`：确认是否成功路由到队列

如果发送失败，就根据 Redis 里的消息元数据按 `msgId` 重试；如果超过最大次数，就进入失败缓存。

### 消费者侧
我没有只依赖业务代码天然幂等，而是专门封装了 `MqDedupService`：
- 消费前先提取 `messageId`
- 用 Redis `SETNX` 写入 `mq:consumed:{msgId}`
- 如果已经存在，说明是重复消息，直接跳过
- 如果业务异常，则删除去重标记，给后续重试留机会

### 死信兜底
AI 审核这条链路还配置了死信交换机和死信队列：
- 正常队列消费多次失败
- 最终进入 `review.audit.dlx.queue`
- 再统一转成人工审核

---

## 4. 为什么我认为这个问题技术含量高

因为这里面不是单个技术点，而是多个点串起来：
- RabbitMQ 确认机制
- Redis 临时消息备份
- 消息重试
- 消费幂等
- 死信队列
- 业务状态机兜底

真正难的不是某一个 API 怎么写，而是要想明白：

> **失败会发生在哪里？每个失败点出现后，系统还能不能自动恢复，或者至少保证业务不乱。**

---

## 5. 面试时怎么总结

可以这样说：

> 我项目里 RabbitMQ 最难的不是“接入”，而是“可靠性补齐”。我最后做的是发送前 Redis 备份消息元数据、发送时用 ConfirmCallback 和 ReturnsCallback 做双确认，消费时再用 `messageId + Redis SETNX` 做幂等，AI 审核失败最终进入死信队列转人工审核。这样我就把消息丢失、重复消费和失败兜底三个问题都补上了。

# 三、难题二：延时任务不是只有一种做法，我是按业务场景拆开的

## 1. 问题背景

项目里其实有两类“订单超时”场景：

1. **订单创建后 30 分钟未确认，自动取消**
2. **订单到店后 30 分钟未消费，自动取消**

一开始我也想统一用一种延时方案全做掉，但后来发现：**这两个场景虽然都叫“30 分钟后取消”，本质上并不一样。**

---

## 2. 我的思考过程

我先拆业务特征：

### 场景 A：下单后未确认取消
这个场景的特点是：
- 触发点非常明确，就是“订单创建时”
- 延迟时长固定，就是 30 分钟
- 到时间后只需要检查一次状态是否还是 `PENDING`

这个场景特别适合 RabbitMQ 的 **TTL + 死信队列**。

### 场景 B：到店后未消费取消
这个场景的特点是：
- 触发时间不是下单时，而是跟 `reservationTime` 强相关
- 到期后不一定立刻取消，还要做兜底判断
- 多实例部署下，同一订单可能被多个节点扫到
- 状态必须仍然是 `CONFIRMED` 才能取消

这个场景如果硬套 RabbitMQ，会变得不够灵活。

所以我最终没有机械地“一把梭全用 MQ”，而是做了拆分。

---

## 3. 最终方案

### 方案一：RabbitMQ TTL + DLX
用于：**订单确认超时自动取消**

思路：
- 订单创建成功后，发送消息到延迟队列
- 队列配置 TTL = 30 分钟
- 消息过期后自动转发到死信交换机
- 由真正的消费队列处理取消逻辑

这个方案的优势是：
- 原生支持
- 结构清晰
- 面试讲解简单

### 方案二：Redis ZSet + 定时任务扫描 + Redis 原生锁 + 数据库条件更新
用于：**到店后 30 分钟未消费自动取消**

思路：
- 按 `reservationTime + 30分钟` 计算执行时间
- 写入 Redis ZSet，score 是执行时间戳
- 定时任务扫描到期数据
- 每条订单先加锁，避免多实例重复处理
- 再用数据库条件更新：只有状态仍为 `CONFIRMED` 才改成 `CANCELLED`

这里我专门做了两层并发保护：

#### 第一层：Redis 原生分布式锁
避免多实例同时处理同一订单。

#### 第二层：数据库条件更新
即便锁层面有竞争或锁失效，数据库层面也要求：
- `where order_no = ? and status = CONFIRMED`

只有满足条件才真正取消，保证最终状态正确。

---

## 4. 这个难题能体现什么思考

这个问题最能体现的是：

> 我不是看到“延时任务”就只会背一种方案，而是会根据业务触发方式、调度灵活度、并发风险、时序特点去选型。

这比单纯说“我会延时队列”更能体现项目思考深度。

---

## 5. 面试时怎么总结

可以这样说：

> 我项目里有两个看起来很像的延时取消场景，但我没有强行统一方案。订单确认超时是固定延迟，适合 RabbitMQ TTL + 死信队列；到店后未消费取消更依赖预约时间和二次状态校验，所以我改用了 Redis ZSet + 定时扫描，并叠加 Redis 分布式锁和数据库条件更新，既保证灵活性，也保证多实例下不会重复取消。

---

# 四、难题三：事务提交和消息发送的一致性问题

## 1. 问题背景

这个问题出现在评价审核和评分刷新两条链路上。

比如 `createReview()`、`approveReview()`、`deleteReview()` 里，都会涉及：
- 先更新数据库
- 再发送 MQ

如果顺序没处理好，就会出现经典问题：
- 数据库事务回滚了，但消息已经发出
- 消费者收到消息后查不到有效数据
- 最终造成业务不一致

---

## 2. 我的思考过程

一开始最直观的写法就是：

```java
@Transactional
public void approveReview(Long id) {
    reviewMapper.updateById(review);
    rabbitTemplate.convertAndSend(...);
}
```

但我很快意识到，这种写法有一个本质风险：

> `convertAndSend()` 执行成功，不代表当前数据库事务最终一定提交成功。

也就是说，消息层面的“成功”早于事务层面的“成功”，顺序是错的。

我当时考虑过几种方案：

### 方案 A：事务里直接发 MQ
最简单，但不安全。

### 方案 B：本地消息表 / Outbox
最严谨，但对当前项目来说实现成本偏高。

### 方案 C：Spring 事务事件
复杂度适中，且能很好解决“事务提交后再发消息”的问题。

最后我选了方案 C。

---

## 3. 最终方案

做法是：
- Service 层事务方法里只负责写库和发布事件
- 真正发送 MQ 的动作，放到 `@TransactionalEventListener(phase = AFTER_COMMIT)` 里

例如：
- `ReviewCreatedEvent`
- `ReviewRatingRefreshEvent`
- `OrderCreatedEvent`

都走同样的思路。

这样就保证：
- 事务提交成功 → 才会发 MQ
- 事务回滚 → 监听器不触发 → 不发 MQ

这实际上是我在项目里把“业务一致性”往前想了一步的体现。

---

## 4. 为什么这个点很适合面试讲

因为它不是背八股，而是一个很典型的真实项目坑：

> 很多人知道要异步解耦，但容易忽略“异步发送的时机”，最后把系统做成了数据和消息不一致。

我讲这个问题时，能体现我不仅会用 MQ，还会考虑：
- 事务边界
- 事件时机
- 最终一致性
- 工程复杂度与收益的平衡

---

## 5. 面试时怎么总结

可以这样说：

> 我项目里专门处理过数据库事务和 MQ 时序不一致的问题。最开始如果直接在事务方法里发 MQ，会有‘数据库回滚但消息已发出’的风险。后来我统一改成 Spring 事件 + `@TransactionalEventListener(AFTER_COMMIT)`，保证事务真正提交成功后再发消息，这样业务数据和消息链路是一致的。

# 五、难题四：AI 多轮对话的会话记忆并不是“存一下 Redis”就结束了

## 1. 问题背景

项目里 AI 助手支持多轮对话、RAG 检索、工具调用和 MCP 联网搜索。  
为了让上下文连续，我把聊天记忆持久化到了 Redis。

本来我以为这部分工作比较直白：
- 从内存拿消息列表
- 序列化后存 Redis
- 下次再反序列化出来

但真正接入后，我发现并没有这么简单。

---

## 2. 具体遇到的问题

在某些会话里，模型会出现异常或者理解错乱。继续排查后我发现，问题不在 Redis 本身，而在于：

> **消息顺序在持久化/恢复后，不一定满足模型的预期。**

特别是 LangChain4j 这类框架下，模型通常假设：
- `SystemMessage` 可以在前
- 但第一条真正参与对话的非系统消息，应该是 `UserMessage`

如果第一条非系统消息不是用户消息，而是 AI 回复或工具结果，模型就容易出现上下文理解异常。

这个问题很隐蔽，因为：
- Redis 里数据是有的
- 反序列化也没报错
- 但模型行为就是“不对”

这类问题最难的地方在于：**功能看起来没坏，但结果明显不稳定。**

---

## 3. 我的定位思路

我当时没有立刻怀疑模型，而是先做了两件事：

1. 打印 Redis 中存储的会话消息顺序
2. 对比内存中原始消息顺序和恢复后的消息顺序

最后我发现，真正需要修的不是“怎么存”，而是“存之前要不要做顺序修复”。

也就是说，这不是 Redis 的问题，而是**消息协议和模型输入预期的匹配问题**。

---

## 4. 最终方案

我没有去改底层框架，而是在 `RedisChatMemoryStore` 里做了一层顺序修复：
- 找到第一条非系统消息
- 如果它不是 `UserMessage`
- 就尝试把第一条用户消息调整到前面

这个方案的优点是：
- 改动面小
- 对现有业务透明
- 能显著提升对话稳定性

---

## 5. 为什么这个难题值得讲

因为它能体现我处理问题时不是只会看异常日志，而是会：
- 先怀疑输入输出是否满足协议约束
- 把“表面现象”和“根本原因”分开
- 找一个对现有系统侵入最小的修复点

这是一类非常真实的工程问题，尤其适合面试时体现“排障和定位能力”。

---

## 6. 面试时怎么总结

可以这样说：

> 我项目里 AI 多轮对话记忆不是简单存在 Redis 就完了，后面我遇到过模型上下文错乱的问题。排查后发现不是 Redis 丢数据，而是消息顺序不满足模型预期：第一条非系统消息应该是用户消息。我最后在自定义的 `RedisChatMemoryStore` 里做了顺序修复，问题才稳定下来。这个问题比较能体现我对 AI 框架协议约束和排障思路的理解。

# 六、可作为补充的一个难题：订单号生成在多实例下如何保证唯一

这个问题可以作为补充，不一定每次都讲，但如果面试官问到“高并发下唯一 ID 怎么生成”，可以拿出来。

## 我的思考过程

我一开始考虑过：
- `时间戳 + 随机数`
- `synchronized`
- 本地自增序列

但这些方案在单机下还行，多实例部署下就不稳了。

后来我把需求重新定义为：
- 不一定要全局趋势有序到纳秒级
- 但必须多实例唯一
- 还要便于肉眼识别日期

最后我采用的是：
- `ORDER + yyyyMMdd + Redis 原子自增序列`

即每天一个 Redis key：
- `order:seq:20250921`

通过 `INCR` 保证多实例下的原子性。当天第一次生成时再设置过期时间，避免无效 `expire` 开销。

## 面试时怎么说

> 订单号生成我最终没有用本地锁，而是改成 Redis 原子自增。因为多实例下本地锁只能限制单机，Redis 的 `INCR` 才能天然保证跨实例唯一。同时我保留了日期前缀，既方便排查，也便于肉眼识别订单生成日期。

# 九、难题五：并发安全的”先查后插”问题（Redisson + 唯一索引双层防护）

## 1. 问题背景

项目里有两个典型的”先查后插”场景：
- 用户注册：先查用户名是否存在，不存在再插入
- 评价提交：先查该订单是否已评价，未评价再插入

一开始这两个逻辑写起来很自然，功能测试也完全正常。但我意识到，**单线程测试通过不代表并发下安全**。

---

## 2. 核心问题：竞态条件（Race Condition）

并发场景下，两个请求同时到达：

```
请求1：查用户名 → 不存在 → （此时请求2也查完了，也发现不存在）→ 插入
请求2：查用户名 → 不存在 → 插入
```

结果：两条相同用户名的数据都插进去了，产生脏数据。

这是典型的”先查后插”竞态条件，在高并发下必然会出现。

---

## 3. 我的思考过程

我考虑过两种方案：

### 方案 A：只加数据库唯一索引
最简单，DB 层面强制约束，并发插入时只有一条能成功，另一条抛 `DuplicateKeyException`。

但问题是：两个请求都打到了 DB，都执行了 insert，只是一个成功一个失败。高并发下无效写入多，DB 压力大。

### 方案 B：只加分布式锁
锁住”查 → 插”整个区间，串行化处理。但如果锁失效或者多节点锁实现有问题，还是可能出现重复插入。

### 最终方案：Redisson 分布式锁 + 数据库唯一索引，两层防护

这两层职责不同：
- **锁**：让并发请求串行化，减少无效 DB 写入，是第一道门
- **唯一索引**：最终兜底，无论锁层面出什么问题，DB 层面绝对不允许重复数据，是最后一道墙

**锁可以没有，索引不能没有。**

---

## 4. 最终方案

### 数据库层
```sql
ALTER TABLE user ADD UNIQUE INDEX uk_username (username);
ALTER TABLE user ADD UNIQUE INDEX uk_phone (phone);
ALTER TABLE review ADD UNIQUE INDEX uk_user_order (user_id, order_id);
```

捕获 `DuplicateKeyException` 转成友好的业务异常：
```java
} catch (DuplicateKeyException e) {
    if (e.getMessage().contains(“uk_username”)) {
        throw new BusinessException(ResultCode.BAD_REQUEST, “用户名已存在”);
    }
    ...
}
```

### 分布式锁层
- 用户注册锁 key：`lock:user:register:{username}`，按用户名粒度加锁，不同用户名互不影响
- 评价提交锁 key：`lock:review:submit:{userId}:{orderId}`，按用户+订单粒度加锁

```java
RLock lock = redissonClient.getLock(lockKey);
boolean locked = lock.tryLock(0, 10, TimeUnit.SECONDS); // 不等待，拿不到直接返回false
if (!locked) {
    throw new BusinessException(ResultCode.BAD_REQUEST, “请勿重复提交”);
}
try {
    // 查重 → 插入
} finally {
    if (lock.isHeldByCurrentThread()) lock.unlock();
}
```

`finally` 里加 `isHeldByCurrentThread()` 判断，防止锁超时后误释放其他线程持有的锁。

---

## 5. 为什么这个点适合面试讲

因为它体现了：
- 知道单线程测试通过不等于并发安全
- 知道”先查后插”是竞态条件，不是偶发 bug
- 知道锁和索引各自的职责，不会只用一种
- `finally` 里的 `isHeldByCurrentThread()` 细节，体现对 Redisson 锁超时场景的理解

---

## 6. 面试时怎么总结

> 我项目里有两个”先查后插”的场景，用户注册和评价提交。并发下这两个场景都有竞态条件风险。我的方案是两层防护：第一层用 Redisson 分布式锁把查和插串行化，锁粒度按用户名或用户+订单维度控制，拿不到锁直接返回；第二层在数据库加唯一索引兜底，捕获 DuplicateKeyException 转成业务异常。锁是减少无效写入的第一道门，索引是绝对不允许脏数据的最后一道墙，两者缺一不可。

---

# 十、难题六：热门榜单刷新的并发保护与幂等设计

## 1. 问题背景

项目里热门榜单提供了手动刷新接口 `POST /api/hot-rank/refresh`，同时还有定时任务每日凌晨2点自动刷新。

刷新逻辑是：
1. 删除旧榜单 ZSet
2. 删除旧详情缓存
3. 查询近30天订单数据
4. 写入新 ZSet
5. 预热详情缓存

---

## 2. 核心问题

如果并发触发两次刷新（比如定时任务和手动刷新同时触发），会出现：
- 线程A删了旧ZSet，线程B也删了
- 线程A查完DB准备写，线程B也查完了
- 两个线程交替写ZSet，数据混乱
- 预热缓存也会被重复执行，浪费资源

---

## 3. 最终方案

用 Redisson `tryLock`，拿不到锁**直接返回**，而不是等待：

```java
RLock lock = redissonClient.getLock(“lock:hot:rank:refresh”);
boolean locked = lock.tryLock(0, 10, TimeUnit.SECONDS);
if (!locked) {
    return; // 已有刷新在进行，直接跳过
}
```

这里选择”拿不到锁直接返回”而不是”等待”，是因为：
- 榜单刷新是幂等操作，同一时刻只需要一个线程执行
- 等待没有意义，第一个线程刷完后数据已经是最新的了
- 直接返回可以避免请求堆积

---

## 4. 面试时怎么总结

> 热门榜单刷新涉及删旧数据、查DB、写ZSet、预热缓存多个步骤，并发触发会导致数据混乱。我用 Redisson tryLock 做了保护，拿不到锁直接返回而不是等待，因为榜单刷新是幂等的，同一时刻只需要一个线程执行，等待没有意义。

# 十一、难题七：ES 同步从同步调用改为 MQ 异步解耦

## 1. 问题背景

评分更新后需要同步 ES，最初的写法是在 `RatingUpdateServiceImpl` 里直接调用：

```java
restaurantIndexService.syncRestaurantById(restaurantId);
```

---

## 2. 核心问题

`RatingUpdateServiceImpl` 本身是 RabbitMQ 消费者调用的。如果 ES 同步是同步调用：
- ES 抖动或超时，会导致消费者处理时间变长
- 消费者处理慢，MQ 消息开始积压
- 积压严重时，评分更新整条链路都会被拖垮

---

## 3. 最终方案

评分写库成功后，发一条 MQ 消息，由专门的 `RestaurantEsSyncConsumer` 消费：

```
评分写库 → 发 restaurant.es.sync 消息 → RestaurantEsSyncConsumer → syncRestaurantById()
```

这样：
- 评分更新消费者不再等待 ES，处理速度快
- ES 同步失败只影响搜索，不影响评分更新主链路
- 两条链路彻底解耦，各自独立重试

---

## 4. 为什么这个点适合面试讲

它体现了一个重要的工程判断：

> 消费者里不应该再做耗时的同步调用，否则会形成”消费者拖慢 → 消息积压 → 整条链路雪崩”的连锁反应。

用 MQ 解耦耗时操作，是分布式系统里防止链路雪崩的常见手段。

---

## 5. 面试时怎么总结

> 评分更新后需要同步 ES，最初是在消费者里直接同步调用。但消费者里做同步 IO 有风险：ES 一旦抖动，消费者处理变慢，消息开始积压，整条链路都会被拖垮。我把 ES 同步改成了再发一条 MQ 消息，由独立的消费者处理，两条链路彻底解耦。评分更新和 ES 同步各自独立重试，互不影响。
