## 素材一：Spring 事务回滚踩坑（推荐首选）

**适用问题：** "你遇到过什么难排查的 bug？" / "说说你踩过的坑"

### 背景

实习期间开发一个工单批量保存接口，一次请求里可以同时新建和更新多条工单任务，要求任意一条失败时整批回滚，不留脏数据。

### 遇到的问题

加了 `@Transactional(rollbackFor = Exception.class)` 注解后进行测试，故意传一个不存在的任务 ID，接口返回了 404 错误，但去数据库一查，第一条新建的数据已经写进去了，**事务并没有回滚**。

### 排查过程

检查代码发现，处理任务不存在的逻辑是：

```java
// 错误写法：正常 return，不触发回滚
return CommonResult.error(ResultCode.NOT_FOUND, "任务不存在");
```

这是正常的方法返回，并不会抛出异常。而 Spring 的 `@Transactional` 本质上是 **AOP 代理**，它只在方法**抛出异常时**才拦截并触发回滚，对普通的 `return` 完全无感知。

### 解决方案

把 `return CommonResult.error(...)` 改成抛出业务异常：

```java
// 正确写法：抛异常触发回滚
throw new Gen2wbException(ResultCode.NOT_FOUND.getCode(), "任务不存在");
```

Spring 事务拦截到异常后触发回滚，再测试验证第一条数据也不会写入。

### 收获

`@Transactional` 不是"方法失败就回滚"，而是"方法**抛出异常**才回滚"。这个细节在教材里很少提，但实际开发中很容易踩坑。

### 追问准备

| 追问 | 参考回答 |
|---|---|
| 除了抛异常还有什么方式手动触发回滚？ | `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()` |
| `@Transactional` 在什么情况下会失效？ | 同类内部方法调用（没走代理）、异常被 catch 住没有重新抛出、方法不是 public |
| 为什么要加 `rollbackFor = Exception.class`？ | Spring 默认只回滚 `RuntimeException`，加上这个参数后 checked exception 也会触发回滚 |

## 素材二：N+1 查询问题与批量优化（技术深度最强）

**适用问题：** "你做过哪些性能优化？" / "说说你遇到过的技术挑战"

### 背景

工单任务列表接口需要同时返回每个任务关联的生图记录，以及每条生图记录对应的 AI 生成图片 URL，数据来自三张不同的表。

### 遇到的问题

最初的思路是循环查询：遍历每个任务查一次图片记录，再对每张图片查一次 AI 生成结果。10 个任务、每个任务 3 张图片，就需要查询 `1 + 10 + 30 = 41` 次数据库，任务量一大性能会急剧下降，这就是典型的 **N+1 问题**。

### 解决方案

改成三步批量查询，数据库查询始终只有 3 次：

```
第1步：收集所有任务 ID → 一次 IN 查询拿到所有图片记录
第2步：提取图片记录中的 AI 任务 ID → 一次 IN 查询拿到所有生成结果
第3步：在内存中用 Collectors.groupingBy 按任务 ID 分组，完成关联组装
```

核心代码思路：

```java
// 批量查图片
List<GalleryTaskImage> allImages = taskImageMapper.selectList(
    new LambdaQueryWrapper<GalleryTaskImage>()
        .in(GalleryTaskImage::getGalleryTaskId, galleryTaskIds)
);

// 批量查生图结果，转成 Map 方便 O(1) 查找
Map<String, AigcTaskResult> resultMap = aigcTaskResultMapper
    .selectByTaskIds(aigcTaskIds)
    .stream()
    .collect(Collectors.toMap(AigcTaskResult::getTaskId, r -> r, (a, b) -> a));

// 内存中按任务 ID 分组
Map<String, List<GalleryTaskImageVo>> imageVoMap = allImages.stream()
    .collect(Collectors.groupingBy(GalleryTaskImageVo::getGalleryTaskId));
```

### 收获

关联查询不能无脑放在循环里，要先**批量取数据再在内存里 join**，这是处理列表类接口的常见思路。`Collectors.groupingBy` 是处理这类场景的利器。

### 追问准备

| 追问 | 参考回答 |
|---|---|
| 如果数据量非常大，IN 查询也会慢怎么办？ | 对 IN 的 ID 列表做分批（每批 500~1000 条），避免单次 IN 过长 |
| 为什么不直接用 SQL JOIN 一次查完？ | JOIN 会产生笛卡尔积，结果集行数膨胀，在 ORM 框架里组装反而更复杂；分步查询更灵活 |

## 素材三：多表关联链路理解（体现系统设计理解）

**适用问题：** "说说你负责模块的业务复杂度" / "你是如何理解这个系统设计的？"

### 背景

工单任务模块涉及三张表：工单任务表、工单图片表、AI 生图结果表，需要在任务列表里展示每个任务关联的 AI 生成图片。

### 遇到的问题

工单图片表上有**两个外键**，一个关联工单任务，一个关联 AI 生图任务，而 AI 生成结果并不是普通的列，而是存在一个 `resultData` 的 **JSON 类型字段**里，key 是 `imageUrls`，值是图片 URL 列表。

刚开始没意识到这一点，直接访问字段取到的一直是 `null`，排查了一段时间才发现需要调封装好的 `getImageUrls()` 方法来取值。

### 理清后的关联链路

```
工单任务（GalleryTask）
    ↓ id → galleryTaskId
工单图片（GalleryTaskImage）—— 同时持有两个外键
    ↓ taskId → taskId
AI生图结果（AigcTaskResult）
    ↓ resultData["imageUrls"]
生成图片 URL 列表
```

```java
// 不能直接取字段，要用封装方法
List<String> imageUrls = aigcTaskResult.getImageUrls(); // 内部从 resultData Map 中取值
```

### 收获

接手陌生模块时要先把每张表的职责和外键关系梳理清楚。遇到 JSON 类型字段不能用普通 ORM 方式直接取值，要先确认是否有封装方法，避免绕弯路。

### 追问准备

| 追问 | 参考回答 |
|---|---|
| 为什么不把生成图片 URL 存成普通列？ | 生图结果结构不固定，可能有图片、文本、视频等多种类型，JSON 字段更灵活扩展 |
| 两个外键在同一张表上，这种设计合理吗？ | 合理，中间表本身就是连接两侧实体的桥梁，既关联工单任务又关联生图任务，职责清晰 |
